# Executive Summary

- **Problem:** I wanted one planner for recurring work, unfinished tasks that roll forward, and subtasks that can become full tasks.
- **My role:** I designed the product, developed the Python/Django backend and data model, implemented authentication and tests, and ran production deployment and verification. I built the Next.js frontend and BFF routes with Claude Code as an implementation partner and reviewed the resulting changes.
- **Key decisions:** Task changes use versioned, transactional commands so stale or partial multi-record writes do not silently overwrite valid state.
- **Outcome:** Picking Up is deployed on Vercel, Cloud Run, and Neon PostgreSQL, and I use it to plan my own work.

## Selected Engineering Contributions

- **Frontend** — Built responsive Daily, Weekly, and Monthly planning workflows for desktop and mobile web, including agenda/timeline modes, full-screen task editing, drag-to-reorder and drag-to-reschedule interactions, and optimistic state reconciliation.
- **Backend — Commands** — Designed six versioned, transactional DRF command endpoints for Nest, Promote, Detach, Delete occurrence, Reschedule, and Reorder. Atomic transactions, row-level locks, and `409 Conflict` responses prevent stale or partial multi-record writes.
- **Backend — Integrity and authentication** — Enforced Unicode-normalized, case-insensitive category uniqueness at the database boundary, and hardened authentication with consistent failure contracts, endpoint-specific burst and sustained throttles, and a production proxy-configuration guard.
- **Deployment** — Migrated production from Oracle Autonomous Database and an OCI VM to Dockerized Django on Cloud Run, Neon PostgreSQL, and a Next.js BFF on Vercel. Verified API health, authentication, and persistent task writes in production.

## Core Functionality

- Daily, Weekly, and Monthly planning over one task model
- Repeating routines with per-date exceptions and rollover
- Drag-to-reschedule and drag-to-reorder
- Subtask notes, task nesting, and promotion back to a standalone task
- Email/password and Google authentication
- Per-user persistence through the Django API

## Architecture

```text
Browser -> Next.js BFF on Vercel -> Django REST API on Cloud Run -> Neon PostgreSQL
```

Next.js keeps JWTs in HTTP-only cookies. Django owns task validation and multi-record transitions through dedicated commands for Nest, Promote, Detach, Delete-occurrence, Reschedule, and Reorder.

Each task has a version. Commands check the expected version, lock the affected rows, and complete inside `transaction.atomic()`. Stale edits return `409 Conflict` instead of overwriting newer state.

## Backend Highlights

- **Atomic task commands** — Replaced client-composed writes with transactional services so one failed request cannot leave half of a task transition committed.
- **Optimistic reconciliation** — The UI updates immediately, while queued field and subtask deltas are rebased onto authoritative server state after a conflict or sync failure.
- **Domain and auth boundaries** — Added cross-field task validation, selected database constraints, consistent Simple JWT failure handling, endpoint throttles, and concurrency-safe registration and Google identity linking.

## Responsive Product Design

The desktop planner keeps timeline and agenda context visible together. For mobile, I moved beyond simply shrinking the same layout and designed a separate information structure around the same task state.

- A compact header and seven-day date strip keep date navigation reachable.
- Persistent bottom navigation switches between Daily, Weekly, and Monthly.
- Daily uses a Tasks/Timeline switch instead of compressing two desktop panes.
- Weekly becomes a stacked agenda, while Monthly becomes a week-grouped date list with a full-screen day agenda.
- Task Details opens full-screen with safe-area-aware actions, mobile-sized controls, and a persistent quick-add path.

## Deployment

I deploy the frontend manually from the Next.js app with Vercel CLI. Its BFF routes use the server-only `DJANGO_API_BASE_URL`, so the browser never calls Django directly.

For the API, I build the Django/Gunicorn Docker image with Cloud Build and deploy the resulting image to Google Cloud Run. Production data runs on Neon PostgreSQL through the pooled connection, and I run database migrations deliberately before the API deployment rather than during container startup. Cloud Run revisions and Vercel deployments provide the rollback points.

For the first live release, I verified Cloud Run health and ran registration, login, and task-creation requests against the deployed API and Neon database. I then exercised the Vercel BFF-to-Cloud Run path through the live registration route.

## Result

Picking Up is an application I use to plan my own work rather than a static demo. Its desktop and mobile layouts now present the same planner state in ways suited to each screen, while the backend owns version conflicts, transaction boundaries, ordering, and task validity.

The main remaining work is server-owned routine materialization and direct production-like concurrency verification. Trusted client-IP propagation through the Vercel BFF and shared throttle state across Cloud Run instances also remain operational follow-ups.
