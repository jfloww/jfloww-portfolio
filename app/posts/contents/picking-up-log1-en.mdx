## Goal

The first goal for Picking Up was a web version where I could sign in and manage real tasks.

The original plan was a UI prototype backed by mock data, with pages such as Today, Inbox, and Done. Once work started, it became clear that the flow was hard to judge without login and persistence. I decided to establish the basic authentication, backend, and database structure alongside the interface.

## Sketch

The frontend and backend were separated so a future iPhone app could use the same API.

```text
frontend/         -> Next.js web app
backend/          -> Django REST API
mobile-frontend/  -> future iPhone app
docs/             -> planning and development notes
```

The browser would not handle JWTs directly.

```text
Login form
  -> Next.js /api/auth/login
  -> Django /api/auth/token/
  -> store JWT in HTTP-only cookies
  -> enter a protected route
```

Tasks started with four scopes instead of being attached only to a date.

```text
day   -> work for a date
week  -> work for a week
month -> work for a month
year  -> goals or notes for a year
```

## Plan

1. Build login and registration first — the screens needed to be tested through a real user flow.
2. Set shared styles for landing and auth — basic UI rules should be stable before more pages were added.
3. Decide how Django connects to Oracle — the production database direction needed to be clear early.
4. Build the task repository and scope model — storage and movement rules came before detailed views.
5. Implement Daily and Weekly first — they were the most useful scales for checking the planner structure.

## Issues During Development

### A mock interface did not show the complete flow

The first plan was close to a frontend-only prototype. A screen that opened directly at `/app` did not answer what happened after login or how user data would be kept separate.

The Phase 1 boundary was expanded slightly to include Django authentication endpoints and a protected route.

```text
POST /api/auth/register/
POST /api/auth/token/
POST /api/auth/token/refresh/
GET  /api/auth/me/
```

Password reset, email verification, OAuth, and MFA remained out of scope. There was no reason to keep expanding authentication before the core task workflow existed.

### Local and production databases were different

SQLite was convenient for local development, but it was not the production target. Production was set around Oracle Autonomous Database 26ai Always Free, with Django reading the connection from environment variables.

```text
ORACLE_DB_USER
ORACLE_DB_PASSWORD
ORACLE_DB_DSN
```

Oracle migrations and tests still needed their own checks. A feature working on local SQLite would not automatically mean that the database work was complete.

### Unfinished tasks needed somewhere to go

Leaving incomplete tasks on old dates would make users search through past views. A rollover rule moved them into the current planning period.

```text
past day task   -> current weekly scope
past week task  -> current week
past month task -> current month
completed task  -> does not move
```

## Completed Flow

As of July 16, the following path worked:

```text
register or sign in
  -> store authentication in HTTP-only cookies
  -> enter the protected planner
  -> view Daily and Weekly tasks
  -> add and complete tasks
  -> roll unfinished past work forward
```

The implemented scope included:

- Next.js login, signup, and protected routing;
- Django JWT authentication endpoints;
- shared landing and auth layouts;
- light and dark theme tokens;
- the task type and scope model;
- a localStorage repository with payload validation;
- rollover logic;
- a React context and reducer store;
- initial Daily and Weekly views.

## Improvements and Notes

- Tasks still live only in localStorage.
- Monthly and Yearly need to be completed.
- Authentication and migrations need another pass against Oracle.
- The next step is turning Daily and Weekly into views that can schedule actual time.
