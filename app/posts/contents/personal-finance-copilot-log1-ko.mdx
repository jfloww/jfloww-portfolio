## 목적

프로젝트는 현실적인 질문에서 시작했다. 다른 도시에서 더 높은 연봉을 받으면 세금, 주거비, 통근, 이사비, benefit, 시간까지 계산한 뒤에도 실제 삶이 나아질까?

대부분의 salary·cost-of-living calculator는 일반적인 평균값을 비교한다. 나는 개인의 실제 조건에서 계산을 시작하고, 결과의 모든 숫자를 다시 확인할 수 있게 만들고 싶었다. 그래서 첫 범위는 AI의 답변이 아니라 deterministic engine에 집중했다. 이후 model이 복잡한 document나 transaction description을 해석할 수는 있지만, arithmetic에는 관여하지 않는 경계를 정했다.

## 스케치

첫 product boundary는 불확실한 input과 정확해야 하는 계산을 분리했다.

```text
current job + candidate offer + personal costs
  -> period와 ownership 정규화
  -> deterministic comparison engine
  -> equivalent salary / break-even / negotiation gap
  -> result + derivation tree
```

Money는 모든 layer에서 exact value로 유지하도록 했다.

```text
Python Decimal
  -> PostgreSQL NUMERIC
  -> JSON string
  -> browser에서 표시
```

Browser에는 money를 JSON number로 보내지 않는다. JavaScript number는 binary floating point이므로 boundary에서 `4217.33`을 number로 바꾸면 backend가 지키려던 정확성을 약하게 만들 수 있었다.

## 계획

1. Money와 period primitive를 먼저 정의한다 — 이후 모든 계산이 이 규칙에 의존한다.
2. Walking skeleton을 일찍 배포한다 — engine이 커지기 전에 실제 숫자 하나와 derivation이 전체 stack을 통과해야 했다.
3. Employment, benefit, household cost, evidence를 model로 만든다 — 숨은 상수 대신 명시적인 input으로 비교하려 했다.
4. Calculator를 solver보다 먼저 만든다 — equivalent salary와 break-even도 main result와 같은 engine을 사용해야 했다.
5. FastAPI와 PostgreSQL로 결과를 노출한다 — 완료된 run을 재현할 수 있는 boundary와 storage가 필요했다.
6. AI, AWS workflow, document extraction은 phase 1 밖에 둔다 — 신뢰할 수 있는 첫 비교를 늦추지 않기 위해서였다.

## 설계하면서 생긴 이슈

### Monthly amount가 12배 틀려도 그럴듯해 보일 수 있었다

Decimal 값만으로는 hourly, biweekly, monthly, annual, one-time 중 어떤 주기인지 알 수 없다. 값과 period가 함께 이동하도록 `PeriodicAmount`를 설계했다.

```text
biweekly     -> 1년에 26회
semimonthly -> 1년에 24회
one-time     -> annualize 불가
```

Period conversion을 여러 calculator에 흩어진 convention이 아니라 domain operation으로 만들었다.

### 하나의 비용을 여러 calculator가 중복 계산할 수 있었다

Housing, commuting, relocation, ordinary living cost는 경계가 쉽게 겹친다. Parking도 발생 이유에 따라 housing 또는 commuting으로 볼 수 있다.

모든 category를 정확히 하나의 owner에 배정하고, 누락되거나 두 곳에서 소유한 category가 있으면 import 단계에서 실패하는 partition check를 두었다. Double counting을 review 주의사항이 아니라 구조적인 규칙으로 만들었다.

### Paystub override가 겉으로는 정상인 채 오래될 수 있었다

첫 phase에는 완전한 tax engine이 없어서 실제 net pay override가 필요했다. 하지만 salary, filing status, pay frequency, 401(k) contribution이 바뀐 뒤에도 같은 값을 사용하면 evidence와 계산이 조용히 분리된다.

Override가 자신을 만든 field의 fingerprint를 보관하고, invalidating field가 바뀌면 `ACTIVE`에서 `STALE`로 전환되게 했다. API도 generic error 대신 어떤 field가 원인인지 알려주도록 설계했다.

### Break-even 날짜 하나만으로는 이후의 역전을 숨길 수 있었다

Relocation cost 때문에 cumulative value가 0을 넘었다가 다시 내려갈 수 있다. Solver는 첫 crossing과 그 뒤로 유지되는 stable break-even month를 모두 반환하도록 했다.

```text
first_crossing_month
stable_break_even_month
```

가장 빠른 답이 항상 지속 가능한 답은 아니기 때문에 둘을 구분했다.

## 정해진 범위

초기 설계에서 다음 규칙을 고정했다.

- exact `Decimal` arithmetic과 이름이 있는 rounding policy
- HTTP boundary에서 string으로 serialize되는 money
- financial input에 포함되는 명시적인 period와 evidence
- double counting을 막는 category ownership
- comparison 반환 전 실행되는 monthly reconciliation
- formula, input, provenance, rounding policy를 가진 derivation
- equivalent-salary, break-even, negotiation-gap solver
- immutable completed run과 idempotent write
- 전체 UI보다 먼저 배포하는 public walking skeleton

첫 phase는 전체 아이디어보다 의도적으로 좁게 잡았다. Federal/state tax 계산, document AI, AWS, public-data pipeline, authentication, multi-user collaboration은 뒤로 미뤘다. 첫 번째 증명은 스스로 계산 근거를 보여줄 수 있는 comparison이어야 했다.

## 개선점과 노트

- 첫 demo는 synthetic profile과 명시적인 net-pay override를 사용한다.
- 다른 UI를 줄이더라도 derivation tree와 reconciliation invariant는 제외하지 않는다.
- Calculation core의 내부 이름은 OfferDelta였고, transaction 영역이 커지면서 product identity는 이후 다시 정리하게 된다.
- 다음 작업은 walking skeleton을 구현하고 exact value 하나가 전체 deployment path를 통과하는지 확인하는 것이다.
