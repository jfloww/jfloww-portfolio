## 시작: 단순한 to-do가 아니라 매일 쓸 수 있는 작업 공간

처음 계획한 Phase 1은 웹 프로토타입이었다. mock data로 UI를 만들고, Today, Inbox, Done, Archived, Settings 같은 화면을 구성한 뒤 task detail panel을 붙이는 정도를 생각했다.

하지만 개발을 시작해보니 단순 mock UI만으로는 실제 앱의 흐름을 확인하기 어려웠다. 로그인하고, 내 데이터가 유지되고, `/app`에 접근하는 흐름까지 있어야 진짜 앱처럼 판단할 수 있었다. 그래서 Phase 1 안에서 인증과 백엔드 foundation 일부를 먼저 당겨서 만들었다.

## 프로젝트 구조와 기술 선택

초기 구조는 다음처럼 잡았다.

```text
frontend/         -> Next.js web app
backend/          -> Django REST API
mobile-frontend/  -> future iPhone app
docs/             -> planning and development history
```

처음에는 Supabase 같은 선택지도 있었지만, 최종적으로 Django + Oracle Database on OCI 방향으로 정했다. 기능 구현뿐 아니라 백엔드, API, 인증, 권한, DB migration, 클라우드 배포까지 직접 다뤄보고 싶었기 때문이다.

Django backend는 인증, 권한, API contract, task data, migration을 담당한다. frontend와 미래의 iPhone app은 같은 API를 사용하게 할 계획이다.

## 인증 foundation

먼저 Next.js frontend에 login, signup page와 protected `/app` route를 만들었다. JWT를 browser localStorage에 직접 저장하지 않고, Next.js route handler를 거쳐 HTTP-only cookie에 저장하도록 구성했다.

현재 인증 흐름은 다음과 같다.

```text
Browser login form
  -> Next.js /api/auth/login
  -> Django /api/auth/token/
  -> Next.js stores JWT in HTTP-only cookies
  -> /app is protected by middleware
```

Django backend에는 다음 인증 endpoint를 만들었다.

```text
POST /api/auth/register/
POST /api/auth/token/
POST /api/auth/token/refresh/
GET  /api/auth/me/
```

이 단계에서 forgot password, email verification, OAuth, MFA 같은 기능은 일부러 뒤로 미뤘다. 아직 핵심 task workflow가 검증되지 않았기 때문에, 인증도 앱을 실제로 사용할 수 있는 최소 수준에 맞췄다.

## 랜딩과 Auth 화면 정리

다음으로 landing, login, signup 화면을 새 디자인 시스템으로 정리했다.

디자인 방향은 Tesla-minimal에 가깝게 잡았다. 흰색/검정색 중심의 절제된 UI에 steel blue accent를 아주 작게만 사용하는 방식이다. dark mode도 포함했고, 기본 theme은 dark로 설정했다.

이 과정에서 Tailwind v4, shadcn/ui, next-themes 기반으로 theme token을 다시 잡았다. `Wordmark`, `ThemeToggle`, `AuthLayout` 같은 공통 컴포넌트를 만들고, login/signup form도 같은 구조로 정리했다.

랜딩 페이지는 아직 실제 task UI가 완성되지 않았기 때문에, 미래의 task workspace를 보여주는 CSS mock을 넣었다. 나중에 `/app`이 완성되면 이 mock은 실제 screenshot으로 교체할 예정이다.

## Oracle Database on OCI

Database는 production 기준으로 Oracle Database on OCI를 사용하기로 했다.

로컬에서는 SQLite를 임시로 쓰고 있지만, production에서는 SQLite를 사용하지 않는 것을 원칙으로 잡았다. Oracle Autonomous Database 26ai Always Free instance를 기준으로 하고, Django settings에서는 `ORACLE_DB_USER`, `ORACLE_DB_PASSWORD`, `ORACLE_DB_DSN` 같은 환경 변수를 통해 연결하도록 정리했다.

현재 문서 기준으로 Oracle migration은 `pickingup_app` user로 적용한 기록이 있고, auth tests를 Oracle Database 대상으로 돌리는 일은 후속 작업으로 남아 있다.

## Task Calendar 설계

이제 핵심 기능인 `/app` task workspace를 만들고 있다.

처음에는 일반적인 to-do list를 생각했지만, 현재 설계는 calendar형 multi-scale view로 발전했다. Daily, Weekly, Monthly, Yearly 네 가지 view가 있고, 기본 view는 Weekly다.

핵심 컨셉은 `zoomed-out context, focused present`다.

예를 들어 Weekly view에서는 한 달 전체를 보여주되, 현재 주만 선명하게 강조한다. Daily view에서는 한 주를 보여주되, 선택된 하루에 집중한다. Monthly view는 1년의 12개월을 보여주고, Yearly view는 연 단위 목표를 다룬다.

task scope는 다음처럼 나뉜다.

```text
day   -> 특정 날짜의 할 일
week  -> 특정 주의 할 일
month -> 특정 달의 할 일
year  -> 특정 해의 목표나 메모
```

또 하나 중요한 기능은 rollover다. 끝내지 못한 task가 과거에 남아 있으면 자동으로 현재 흐름으로 따라오게 한다. 지난 날짜의 미완료 task는 weekly cell로 넘어오고, 지난 week task는 현재 week로 따라오며, 지난 month task는 현재 month로 이동한다. 완료된 task는 건드리지 않는다.

## 현재 구현 상태

현재 `feat/task-calendar` 브랜치에서 다음 작업이 완료되어 있다.

```text
1. Vitest test setup
2. date utility functions
3. task type / scope model
4. rollover logic
5. localStorage repository
6. repository payload validation
7. React context + reducer store
8. quick-add, task-item, period-cell, scope-tasks primitives
9. Weekly view
10. Daily view
```

즉, task calendar의 기반 로직과 주/일 단위 UI는 어느 정도 올라온 상태다.

현재 작업 중인 것은 Monthly / Yearly view다. 파일은 생성되어 있지만 아직 미커밋 상태다. 그 다음에는 view switcher, TaskCalendar shell, `/app` page integration을 붙이면 Phase 1의 task workspace가 거의 완성된다.

## 이번 로그 기준의 결론

처음 Phase 1은 웹 UI 프로토타입 정도였지만, 실제로는 앱의 foundation을 훨씬 넓게 잡게 됐다.

지금까지 완료한 것은 다음에 가깝다.

```text
- 프로젝트 구조 정리
- Django backend 방향 확정
- Oracle Database on OCI 방향 확정
- 인증 foundation 구현
- protected app route 구성
- landing/login/signup 디자인 리빌드
- dark-default theme system 구성
- task calendar 설계
- task calendar 핵심 로직과 Daily/Weekly view 구현
```

아직 남은 것은 task API와 production 품질이다. task calendar UI를 마무리한 뒤, Django `tasks` app과 API를 만들고, localStorage repository를 Django API repository로 교체하는 것이 다음 큰 단계다.

Phase 1의 목표는 이제 명확하다. 보이는 화면을 만드는 것이 아니라, 내가 실제로 로그인해서 들어가고, 할 일을 추가하고, 날짜/주/월 단위로 관리할 수 있는 첫 번째 usable version을 완성하는 것이다.
