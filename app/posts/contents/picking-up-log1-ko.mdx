## 목적

Picking Up의 첫 목표는 로그인해서 실제로 할 일을 관리할 수 있는 웹 버전을 만드는 것이었다.

처음에는 mock data로 Today, Inbox, Done 같은 화면만 만들 생각이었다. 작업을 시작해보니 로그인과 데이터 저장 없이 UI만 확인해서는 앱의 흐름을 판단하기 어려웠다. 그래서 화면 작업과 함께 인증, backend, database의 기본 구조도 잡기로 했다.

## 스케치

프로젝트는 frontend와 backend를 분리하고, 나중에 iPhone app이 같은 API를 사용할 수 있게 구성했다.

```text
frontend/         -> Next.js web app
backend/          -> Django REST API
mobile-frontend/  -> future iPhone app
docs/             -> planning and development notes
```

인증은 browser가 JWT를 직접 다루지 않는 방식으로 잡았다.

```text
Login form
  -> Next.js /api/auth/login
  -> Django /api/auth/token/
  -> JWT를 HTTP-only cookie에 저장
  -> protected route 진입
```

플래너는 task를 날짜 하나에만 묶지 않고 네 가지 scope로 나누는 방향으로 시작했다.

```text
day   -> 특정 날짜의 할 일
week  -> 특정 주의 할 일
month -> 특정 달의 할 일
year  -> 특정 해의 목표나 메모
```

## 계획

1. 로그인과 회원가입을 먼저 만든다 — 실제 사용자 흐름으로 화면을 확인하기 위해 필요했다.
2. landing과 auth 화면의 공통 스타일을 정리한다 — 기능을 늘리기 전에 기본 UI 규칙을 맞추려 했다.
3. Django와 Oracle 연결 방식을 정한다 — production database 방향을 초기에 고정해두고 싶었다.
4. task repository와 scope model을 만든다 — 화면보다 먼저 저장과 이동 규칙이 필요했다.
5. Daily와 Weekly부터 구현한다 — 가장 자주 사용할 단위에서 플래너 구조를 검증하려 했다.

## 만들면서 생긴 이슈

### Mock UI만으로는 사용 흐름을 확인하기 어려웠다

처음 계획은 frontend prototype에 가까웠다. 하지만 `/app`에 바로 들어가는 화면만으로는 로그인 후 어디로 이동하는지, 사용자별 데이터가 어떻게 유지될지 확인할 수 없었다.

Phase 1 범위를 조금 넓혀 Django 인증 endpoint와 protected route를 먼저 붙였다.

```text
POST /api/auth/register/
POST /api/auth/token/
POST /api/auth/token/refresh/
GET  /api/auth/me/
```

비밀번호 재설정, email verification, OAuth, MFA는 이 단계에서 제외했다. 핵심 task workflow를 만들기 전에 인증 기능만 계속 늘리지 않기 위해서였다.

### 로컬과 production database가 달랐다

로컬 개발은 SQLite가 간단했지만 production까지 SQLite를 사용할 생각은 없었다. production은 Oracle Autonomous Database 26ai Always Free를 기준으로 정하고, Django settings에서 환경 변수로 연결하도록 구성했다.

```text
ORACLE_DB_USER
ORACLE_DB_PASSWORD
ORACLE_DB_DSN
```

Oracle migration과 test는 별도 확인이 필요했기 때문에, 로컬에서 동작한다는 이유만으로 database 작업이 끝난 것으로 보지 않기로 했다.

### 끝내지 못한 task의 위치가 애매했다

날짜가 지난 미완료 task를 그대로 두면 사용자가 매번 과거 화면을 찾아가야 했다. 이를 줄이기 위해 rollover 규칙을 추가했다.

```text
지난 day task   -> 현재 weekly scope
지난 week task  -> 현재 week
지난 month task -> 현재 month
완료된 task     -> 이동하지 않음
```

## 완성된 흐름

7월 16일 기준으로 다음 흐름이 동작했다.

```text
회원가입 또는 로그인
  -> HTTP-only cookie에 인증 정보 저장
  -> protected planner 진입
  -> Daily / Weekly task 확인
  -> task 추가와 완료
  -> 지난 미완료 task rollover
```

구현된 범위는 다음과 같다.

- Next.js login, signup, protected route
- Django JWT 인증 endpoint
- landing과 auth 공통 layout
- light/dark theme token
- task type과 scope model
- localStorage repository와 payload validation
- rollover logic
- React context와 reducer store
- Daily와 Weekly의 기본 화면

## 개선점과 노트

- task는 아직 localStorage에만 저장된다.
- Monthly와 Yearly 화면은 마무리가 필요하다.
- Oracle 환경에서 auth와 migration test를 다시 확인해야 한다.
- 다음 작업은 Daily와 Weekly를 실제로 시간을 계획할 수 있는 화면으로 바꾸는 것이다.
