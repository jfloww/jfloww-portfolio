## What Picking Up Became

`Picking Up` began as a small to-do app for my own daily use. The first plan was desktop-first, stored tasks in localStorage, and targeted Oracle on OCI. The product changed as I used it, connected real persistence, reviewed failure cases, and built a mobile-specific experience.

This page is the current-state overview as of August 9, 2026. Logs 1–5 preserve what was true at each stage rather than rewriting the development history to look linear.

## Current Product

The planner now supports:

- Daily, Weekly, and Monthly planning over one task model;
- repeating routines, per-date exceptions, and unfinished-task rollover;
- drag-to-reschedule, drag-to-reorder, and task/subtask transitions;
- task notes, subtask notes, nesting, detaching, and promotion;
- email/password and Google authentication; and
- per-user persistence through the Django API.

Yearly was an early planning idea, but it is not part of the current product. Bucket List resources and UI were implemented during development, then the navigation entry was hidden while the product direction is reconsidered. The visible planner therefore stays focused on Daily, Weekly, and Monthly.

## Current Architecture

```text
Browser
  -> Next.js BFF on Vercel
  -> Django REST API on Google Cloud Run
  -> Neon PostgreSQL
```

The browser communicates with same-origin Next.js routes. The BFF stores JWTs in HTTP-only cookies and attaches the access token to server-to-server Django requests. Django is the persistent authority for users, categories, and tasks. localStorage remains only as a one-time import source for data created before the API migration.

## Responsive Product Design

The desktop planner keeps more context visible: Daily presents the timeline and agenda together, while Weekly and Monthly use wider calendar layouts.

Mobile is not a compressed desktop layout. It has a dedicated information structure:

- a compact calendar header and seven-day date strip;
- persistent Daily, Weekly, and Monthly bottom navigation;
- a Tasks/Timeline switch for the Daily view;
- a vertically stacked Weekly agenda;
- a week-grouped Monthly list with a full-screen day agenda;
- full-screen Task Details with safe-area-aware actions; and
- persistent quick-add controls and touch targets designed around mobile use.

The selected date and task data stay shared across these presentations, so the responsive layouts do not create separate product behavior.

## Reliability Boundaries

The frontend applies optimistic updates, but Django owns valid state transitions. Each task has a version, stale writes return `409 Conflict`, and multi-record actions such as Nest, Promote, Detach, Delete occurrence, Reschedule, and Reorder run as atomic commands with row locking.

After a failed mutation, queued intent is reapplied to authoritative server state rather than saving an old task snapshot. Cross-field serializer validation and selected database constraints protect task rules even when a request bypasses the current UI.

## Why the Original Plan Changed

### localStorage became an API-backed repository

localStorage made the first calendar interactions fast to prototype, but it could not provide cross-device data or meaningful server-side ownership. Connecting the Django API also exposed partial writes, stale optimistic state, and authentication boundaries that did not exist in the browser-only version. The repository interface stayed; its production implementation changed.

### Oracle and OCI became Neon and Cloud Run

Oracle Autonomous Database was suspected of contributing to slow API responses. Because the Django settings and migrations were already portable, the schema and test suite could be verified against an empty Neon branch without rewriting the domain model.

Moving the backend from the OCI VM to Cloud Run was a separate decision. A Dockerfile replaced the initial buildpacks plan so the image build, runtime user, static assets, startup command, and migration boundary remained explicit. Cloud Build also avoids producing an ARM image on an Apple Silicon machine for Cloud Run's Linux/AMD64 runtime.

### Responsive support became a mobile-specific workflow

The first plan treated mobile as a narrower version of the desktop app. In practice, the desktop split panes and calendar grids did not produce a useful small-screen workflow. The final mobile structure therefore uses its own navigation and presentation while preserving the same planner state and actions.

## Production and Next Work

Production releases are intentionally manual. I deploy the frontend with Vercel CLI, build the backend image with Cloud Build, and deploy an immutable Cloud Run revision. Database migrations run as a deliberate step before dependent backend code, never during container startup.

The main remaining engineering work is moving routine occurrence materialization fully to an idempotent server command. Shared throttling across multiple Cloud Run instances and automated deployment can follow when the application's traffic and release frequency justify them.
