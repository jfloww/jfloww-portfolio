## 목적

처음 포트폴리오를 만들 때는 몇 개의 Project와 소개 페이지를 보여주는 것이 전부였다. Post가 늘고 한글 route가 추가되면서 같은 content를 여러 화면에서 읽고, locale별 파일을 하나의 글처럼 다뤄야 했다.

이번 정리는 새 기능을 많이 넣는 작업보다 content와 layout의 책임을 줄이는 작업이었다. Project와 Post는 파일만 추가하면 노출되게 만들고, 페이지는 content 종류가 늘어도 같은 구조를 유지하도록 했다. 화면에서는 section마다 배경색을 바꾸던 구성을 없애고 하나의 surface 위에서 spacing과 divider로 구분하도록 바꿨다.

## 기존 구조에서 불편했던 점

- content가 늘 때마다 list와 detail에서 같은 metadata 처리를 반복하기 쉬웠다.
- 영문과 한글 MDX가 list에서 서로 다른 글처럼 보일 수 있었다.
- Home의 section background가 번갈아 바뀌면서 header와 첫 section의 색 조합이 어색했다.
- Project detail의 image slider가 본문보다 먼저 큰 영역을 차지했지만, list cover와 같은 이미지를 다시 보여주는 경우가 많았다.
- dark mode를 client mount 뒤에 적용하면 첫 paint에서 밝은 화면이 잠깐 보일 수 있었다.

## 스케치

content 경로는 다음처럼 정리했다.

```text
MDX file
  -> gray-matter frontmatter
  -> normalizeContentMeta
  -> visibility / locale grouping
  -> date + id sorting
  -> static list and detail route
  -> server-rendered MDX
```

Project와 Post는 같은 `ContentMeta`를 사용한다. 차이는 파일 위치와 화면 표현에만 두고, loader가 file system 접근과 metadata 규칙을 한곳에서 담당한다.

## Content loader 정리

`getContentPaths()`가 MDX 파일을 찾고, underscore로 시작하는 template은 list에서 제외한다. 각 파일은 `gray-matter`로 frontmatter와 body를 나눈 뒤 `normalizeContentMeta()`를 통과한다.

normalize 단계에서는 다음을 처리한다.

- 빠진 `id`와 `title`의 fallback
- `YYYYMMDD` date format 확인
- `hidden`과 `draft` visibility
- tag와 image array의 잘못된 entry 제거
- locale과 `translationKey` normalization

page component는 file path나 parsing 방식을 알 필요 없이 정리된 metadata와 MDX body만 받는다.

날짜가 같은 글에는 ID를 secondary sort key로 사용한다. 같은 날 작성한 Log 4와 Log 5처럼 date만으로 순서가 정해지지 않는 경우에도 최신 번호가 먼저 보이게 했다.

## Locale 파일을 하나의 글로 묶기

영문과 한글 Post는 파일이 두 개지만 화면에서는 하나의 logical entry다.

```text
picking-up-log5-en.mdx
picking-up-log5-ko.mdx
  -> translationKey: picking-up-log5
```

loader는 먼저 `translationKey`로 group을 만든다. 그다음 요청 locale, English, locale이 없는 파일 순서로 fallback을 선택하고 마지막에 sort와 limit을 적용한다.

이 순서가 중요했다. locale 선택 전에 단순히 file list를 제한하면 한 글의 두 번역이 Home의 두 자리를 차지하거나, 원하는 언어 파일이 limit 밖으로 밀릴 수 있다.

English route는 root를 사용하고 Korean route는 `/ko` prefix를 사용한다. header와 footer도 현재 pathname에서 locale을 읽어 같은 언어의 About, Projects, Posts, Contact로 이동한다.

Project body는 아직 locale-neutral English 파일이 많다. list description은 locale별로 제공하지만 detail body 전체 번역은 다음 작업으로 남겨 두었다.

## MDX rendering과 Next.js runtime

content body는 `next-mdx-remote`로 server에서 compile한다. Next.js 16 development runtime과 `next-mdx-remote/rsc`가 만든 component의 React runtime이 달라지는 문제가 있어, compiled source를 현재 환경의 `jsx-runtime` 또는 `jsx-dev-runtime`으로 실행하도록 `renderMdx()` 경계를 따로 뒀다.

이 처리는 각 detail page에 흩어 놓지 않았다. Project와 Post 모두 같은 renderer를 사용하므로 runtime 관련 변경도 한 파일에서 확인할 수 있다.

## 화면을 하나의 surface로 변경

이전 Home은 section마다 `background`와 `surface-subtle`을 번갈아 사용했다. 각각의 section만 보면 정돈되어 있었지만 전체 화면에서는 header, hero, Projects가 서로 다른 panel처럼 끊겨 보였다.

현재는 header부터 footer까지 같은 background를 유지한다. section 사이는 색 대신 다음 요소로 구분한다.

- shared `PageShell` width
- 일정한 vertical padding
- 얇은 divider
- heading과 description의 간격
- Project card와 Post list 자체의 구조

Contact처럼 content가 적은 페이지는 `PageHeader`의 compact variant를 사용해 header padding과 form spacing을 줄였다. Home section padding도 줄여 화면이 비어 보이지 않게 했다.

Project detail의 image slider는 제거했다. cover는 Projects list에서 project를 구분하는 역할만 하고, detail은 title과 metadata 다음에 본문이 바로 시작한다. Project마다 `showSlider`를 관리할 필요도 없어져 schema와 route props도 함께 줄었다.

## Server와 client 경계

content discovery, locale selection, MDX compile은 server에서 처리한다. client component가 필요한 부분은 실제 interaction이 있는 곳으로 제한했다.

- mobile navigation
- language menu
- dark mode toggle
- Post category filter
- Contact form

theme은 component가 mount된 뒤에만 바꾸지 않는다. document head의 작은 script가 localStorage preference와 system dark-mode preference를 읽어 첫 paint 전에 `<html>` class를 설정한다. toggle은 이후 preference를 저장하고 같은 class를 갱신한다.

## Contact API

Contact form은 Next.js route handler에 name, email, message를 보낸다. server는 whitespace를 정리하고 required 값, email format, 최대 길이를 확인한 뒤 Nodemailer로 전송한다.

응답은 입력 오류 `400`, 짧은 시간의 반복 요청 `429`, mail configuration 또는 전송 실패 `500`으로 나눴다. UI는 성공과 실패 상태를 `aria-live` 영역에 표시한다.

현재 rate limit은 process memory의 `Map`을 사용한다. 한 instance에서 반복 submit을 줄이는 정도이며, 여러 server instance가 공유하는 보안 경계는 아니다.

## 완성된 흐름

```text
새 MDX 작성
  -> frontmatter와 body parse
  -> locale별 logical entry 선택
  -> Home / archive list에 노출
  -> static detail route 생성
  -> shared layout에서 server rendering
```

이번 refactor에서 완료한 내용은 다음과 같다.

- Project와 Post의 공통 content schema와 loader
- locale grouping, fallback, stable ordering
- server-side MDX rendering boundary
- continuous-surface Home과 compact page header
- Project detail image slider 제거
- 첫 paint 전에 적용되는 theme preference
- 입력 validation과 상태 구분이 있는 Contact route
- Project와 Post의 locale별 list summary

## 개선점과 노트

- Project detail body의 한글 번역은 아직 완성되지 않았다.
- 잘못된 frontmatter를 fallback으로 처리하는 대신 build를 실패시킬 strict validation mode를 추가할 수 있다.
- Contact rate limit은 distributed storage를 사용하지 않는다.
- content 수정에는 아직 repository commit과 deploy가 필요하다.
- accessibility audit과 visual regression test는 자동화되어 있지 않다.
