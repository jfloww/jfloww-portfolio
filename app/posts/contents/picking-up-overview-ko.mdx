## Picking Up이 현재 모습이 되기까지

`Picking Up`은 내가 매일 사용하기 위한 작은 to-do app으로 시작했다. 최초 계획은 desktop-first였고, task를 localStorage에 저장했으며, Oracle과 OCI를 production 목표로 두었다. 직접 사용하고, 실제 영구 저장을 연결하고, failure case를 검토하고, 모바일 전용 경험을 만들면서 제품의 형태가 달라졌다.

이 글은 2026년 8월 9일 기준의 현재 상태를 설명한다. Log 1–5는 개발 과정이 처음부터 직선적이었던 것처럼 다시 쓰지 않고, 각 시점에 실제로 맞았던 내용을 그대로 보존한다.

## 현재 제품

현재 planner는 다음 기능을 제공한다.

- 하나의 task model을 사용하는 Daily, Weekly, Monthly 계획
- 반복 routine, 날짜별 예외, 끝내지 못한 task의 rollover
- drag-to-reschedule, drag-to-reorder, task/subtask 전환
- task와 subtask notes, nesting, detach, promote
- email/password와 Google 인증
- Django API를 통한 사용자별 영구 저장

Yearly는 초기 기획에 있었지만 현재 제품에는 포함하지 않았다. Bucket List resource와 UI도 개발 과정에서 구현했지만, 제품 방향을 다시 판단하기 위해 navigation entry를 숨겼다. 현재 사용자에게 보이는 planner는 Daily, Weekly, Monthly에 집중한다.

## 현재 Architecture

```text
Browser
  -> Vercel의 Next.js BFF
  -> Google Cloud Run의 Django REST API
  -> Neon PostgreSQL
```

browser는 same-origin Next.js route와 통신한다. BFF가 JWT를 HTTP-only cookie에 저장하고 server-to-server Django request에 access token을 붙인다. Django는 user, category, task의 영구 저장 authority다. localStorage는 API 연결 전에 만들어 둔 데이터를 한 번 옮기기 위한 legacy import source로만 남아 있다.

## Responsive Product Design

desktop planner는 더 많은 맥락을 한 화면에 유지한다. Daily는 timeline과 agenda를 함께 보여주고, Weekly와 Monthly는 넓은 calendar layout을 사용한다.

모바일은 desktop을 단순히 줄인 화면이 아니다. 별도의 information structure를 적용했다.

- compact calendar header와 7일 date strip
- 항상 접근 가능한 Daily, Weekly, Monthly bottom navigation
- Daily의 Tasks/Timeline 화면 전환
- 세로로 쌓이는 Weekly agenda
- week 단위 Monthly list와 full-screen day agenda
- safe area를 반영한 full-screen Task Details
- 모바일 사용을 고려한 persistent quick-add와 touch target

선택한 날짜와 task data는 두 presentation에서 공유한다. 반응형 layout이 별도의 제품 동작을 만들지는 않는다.

## Reliability Boundary

frontend는 optimistic update를 적용하지만 유효한 상태 전환은 Django가 책임진다. 각 task에는 version이 있고, stale write는 `409 Conflict`를 반환한다. Nest, Promote, Detach, Delete occurrence, Reschedule, Reorder처럼 여러 record를 다루는 action은 row lock을 사용하는 atomic command로 실행한다.

mutation이 실패하면 오래된 task snapshot을 다시 저장하지 않고, 남아 있는 intent를 authoritative server state 위에 재적용한다. cross-field serializer validation과 필요한 database constraint는 현재 UI를 우회한 request에서도 task rule을 보호한다.

## 최초 계획을 바꾼 이유

### localStorage에서 API-backed repository로

localStorage는 첫 calendar interaction을 빠르게 실험하기에는 적합했지만, 여러 기기에서 같은 데이터를 사용하거나 server-side ownership을 보장할 수 없었다. Django API를 연결하면서 browser-only 구조에는 없던 partial write, stale optimistic state, authentication boundary도 드러났다. repository interface는 유지하고 production 구현을 바꿨다.

### Oracle과 OCI에서 Neon과 Cloud Run으로

Oracle Autonomous Database가 느린 API response의 원인일 가능성이 있었다. Django settings와 migration을 이미 여러 database에서 동작하도록 작성해 둔 덕분에 domain model을 다시 만들지 않고 빈 Neon branch에서 schema와 test suite를 검증할 수 있었다.

OCI VM에서 Cloud Run으로 backend를 옮긴 것은 별도의 결정이었다. 처음 검토한 buildpacks 대신 Dockerfile을 사용해 image build, runtime user, static asset, startup command, migration boundary를 직접 확인할 수 있게 했다. Cloud Build를 사용한 이유는 Apple Silicon에서 만든 ARM image와 Cloud Run의 Linux/AMD64 runtime이 달라지는 문제를 피하기 위해서이기도 했다.

### Responsive 지원에서 모바일 전용 workflow로

처음에는 모바일을 desktop app의 좁은 형태로 생각했다. 실제로는 desktop의 split pane과 calendar grid를 줄이는 것만으로 작은 화면에서 유용한 workflow가 되지 않았다. 그래서 같은 planner state와 action을 유지하면서 navigation과 presentation은 모바일에 맞게 따로 구성했다.

## Production과 다음 작업

production release는 의도적으로 수동으로 진행한다. frontend는 Vercel CLI로 배포하고, backend image는 Cloud Build에서 만든 뒤 immutable Cloud Run revision으로 배포한다. database migration은 container startup에서 자동 실행하지 않고, 해당 schema에 의존하는 backend code보다 먼저 별도 단계로 실행한다.

현재 가장 중요한 남은 작업은 routine occurrence materialization을 idempotent server command로 완전히 옮기는 것이다. Vercel BFF의 trusted client-IP 전달, 여러 Cloud Run instance가 공유하는 throttle cache, 자동 배포는 실제 traffic과 release 빈도가 필요해질 때 진행할 수 있다.
