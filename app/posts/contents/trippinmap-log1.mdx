## Goal

TripPinMap started as a way to keep visited places, planned trips, and wishlist destinations on one map.

Travel notes were spread across map bookmarks, photos, and note apps. The first task was not implementation. It was deciding what one saved place should contain and keeping the first version small enough to build.

## Sketch

The map is the main entry point. Each pin has one of three statuses, and its detail fields change with that status.

```text
World map
  └─ Location pin
       ├─ visited  -> dates, timeline, photos, notes
       ├─ planned  -> dates, planned activities
       └─ wishlist -> things to do, notes
```

The basic user flow is:

```text
sign in
  -> open the world map
  -> add a location and status
  -> fill in the matching details
  -> return to the updated map
```

## Plan

1. Fix the three status meanings — their required fields will shape the data model.
2. Keep the map as the first screen — the product is about seeing places together, not browsing a list first.
3. Start with simple text records — a full media pipeline would make the first version much larger.
4. Decide the stack and data ownership next — implementation should start after the product boundary is stable.
5. Draft the database and API after the stack decision — this avoids designing the same contract twice.

## Completed Flow

This log completes the planning boundary, not an implemented application.

The first version includes:

- Google login;
- a world map with status-colored pins;
- create, read, update, and delete for saved places;
- detail fields that change by status;
- basic activity or timeline text records.

The three statuses are defined as follows:

```text
visited  -> visit dates and history, with optional photos and notes
planned  -> planned dates, with optional timeline and checklist
wishlist -> destination, with optional ideas and notes
```

## Improvements and Notes

- Advanced sharing is outside the first version.
- AI recommendations are not part of the initial scope.
- Offline-first support and photo optimization come later.
- Mobile map interaction needs an early prototype before the rest of the UI is finalized.
- The next log should choose the stack and define backend ownership.
