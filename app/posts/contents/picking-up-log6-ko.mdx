## 목적

이번 Log는 Picking Up의 프로덕션 배포 구성을 정리한 기록이다. CI/CD를 붙이기 전에도 내가 직접 운영하고 확인할 수 있는 release flow가 필요해서, 현재 배포는 의도적으로 수동으로 진행한다.

서비스는 [pickingup.vercel.app](https://pickingup.vercel.app/)에서 확인할 수 있다.

## 배포 계획을 바꾼 이유

최초 production 목표는 Oracle Autonomous Database를 사용하는 OCI VM이었다. Oracle이 느린 API response의 원인일 가능성이 있어, 먼저 portable하게 작성한 Django schema와 test suite를 빈 Neon PostgreSQL branch에서 검증했다.

backend compute를 Cloud Run으로 옮긴 것은 그 다음의 별도 단계였다. image build, runtime user, static asset, startup command, migration boundary를 직접 확인하고 설명할 수 있도록 처음 검토한 buildpacks 방식 대신 Dockerfile을 선택했다. 전체 경로를 직접 운영하고 검증하기 전까지는 deployment를 수동으로 유지했다.

## Production Topology

```text
Browser
  -> Vercel의 Next.js BFF
  -> Google Cloud Run의 Django REST API
  -> Neon PostgreSQL
```

browser는 Django를 직접 호출하지 않고 Next.js와 통신한다. BFF가 API base URL을 server-side에만 두고, browser cookie와 proxy 경계를 계속 담당한다.

## Frontend: Vercel

frontend는 `frontend/` directory에서 Vercel CLI로 수동 배포한다.

```bash
vercel --prod
```

`DJANGO_API_BASE_URL`은 server-side environment variable로 설정한다. 이 값을 바꾸면 frontend를 다시 배포해야 하므로 release 경계가 명확하다. Git push만으로 production이 자동 배포되지는 않는다.

## Backend: Cloud Run

Django API는 Docker 안에서 Gunicorn으로 실행된다. 배포 전에는 container를 local에서 build하고 실행한 뒤 `GET /api/health/`를 확인한다. 그 다음 Cloud Build로 production image를 만들고 Artifact Registry에 올린 뒤 Cloud Run에 배포한다.

```text
local Docker health check
  -> Cloud Build image build
  -> Artifact Registry
  -> Cloud Run revision
```

Apple Silicon 개발 환경에서 Cloud Run의 Linux/AMD64 runtime과 다른 ARM image가 만들어지는 문제를 피하기 위해 Cloud Build를 사용했다. Cloud Run은 새 revision이 정상 상태가 된 뒤에 traffic을 받는다.

## Database와 Migration

production은 Neon의 production branch를 사용한다. local 개발은 direct connection을 사용할 수 있고, Cloud Run에서는 짧게 살아나는 serverless connection에 맞게 Neon의 pooled connection string을 사용한다.

migration은 의도적으로 분리한 release step이다.

```bash
python manage.py migrate
```

schema에 의존하는 code를 배포하기 전에 실행한다. API container가 startup 때 migration을 실행하지 않도록 해서 여러 instance가 동시에 migration을 실행하거나 rollout이 database 작업에 막히지 않게 했다.

## 확인과 Rollback

첫 Cloud Run release에서는 `GET /api/health/`을 확인한 뒤 live API를 대상으로 register → login → create-task smoke test를 실행했다. test user와 task가 Neon에 저장된 것을 확인하고 임시 data를 삭제했다.

Vercel 연결 뒤에는 live frontend가 열리는지 확인하고, registration이 Vercel BFF → Cloud Run → Neon 전체 경로를 통과하는지 검증했다. 이 결과로 배포된 authentication boundary와 backend의 persistent write path를 확인했다. 전체 browser task CRUD는 자동 deployment gate가 아니라 release마다 수행할 manual check로 남아 있다.

Cloud Run은 immutable revision을 보관하므로 이전에 정상적이었던 revision으로 traffic을 되돌릴 수 있다. frontend 문제는 Vercel에서 이전 deployment를 promote하는 방식으로 rollback할 수 있다.

## 현재 운영 한계

authentication에는 endpoint별 burst와 sustained throttle이 있고, production은 trusted proxy count가 명시되지 않으면 시작되지 않는다. 하지만 현재 Next.js BFF는 원래 browser client IP를 Django에 전달하지 않는다. 따라서 Vercel topology에서 browser별 IP isolation이 증명됐다고 보지 않는다. trusted client-IP 전달 또는 edge-side limiting이 후속 작업으로 남아 있다.

Django throttle cache도 각 Cloud Run instance의 local state다. 여러 instance가 하나의 global throttle budget을 공유한다고 말하려면 shared cache가 필요하다.

## 이 구성에서 얻은 점

- browser와 Django 사이의 작은 BFF 경계
- frontend와 backend를 각각 확인할 수 있는 release
- 명시적인 database migration 시점
- 두 hosting platform에서 확보한 rollback 경로
- production 보장을 과장하지 않고 명시한 현재 한계

지금은 이 수동 flow가 맞는 선택이다. application이 계속 바뀌는 동안에도 production change를 쉽게 추적할 수 있기 때문이다.
