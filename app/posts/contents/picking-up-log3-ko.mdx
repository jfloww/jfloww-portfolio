## 목적

7월 23일까지 Picking Up은 Daily와 Weekly에서 시간을 계획할 수 있었지만, task는 한 browser의 localStorage에만 저장됐다. 다른 기기에서 로그인하면 같은 데이터를 볼 수 없었다.

7월 24일부터 Bucket List 작업 직전인 7월 30일 오전까지는 task를 사용자 계정에 저장하는 작업을 중심으로 진행했다. 그 과정에서 routine의 한 번짜리 예외, due date, Weekly 날짜 이동, Monthly 화면, Google 로그인도 함께 정리했다.

## 스케치

task 저장 경로는 기존 HTTP-only cookie 인증을 그대로 사용하는 구조로 잡았다.

```text
Planner UI
  -> TaskRepository
  -> Next.js /api/tasks
  -> Django REST API
  -> authenticated user's tasks
  -> Oracle Database
```

browser JavaScript는 JWT를 직접 읽지 않는다. Next.js route handler가 cookie의 token으로 Django에 요청하고 결과만 frontend에 돌려준다.

Django의 task는 user에게 속하며, routine occurrence는 같은 user의 anchor를 참조한다.

```text
User
  └─ Tasks
       ├─ routine anchor
       │    └─ occurrences
       └─ regular task
```

## 계획

1. routine occurrence를 분리하는 기능을 먼저 만든다 — API로 옮기기 전에 task 편집 규칙을 정리할 필요가 있었다.
2. scope와 별개의 due date를 추가한다 — 작업 위치와 마감일은 다른 정보였다.
3. Django task CRUD API를 만든다 — 사용자별 저장 공간이 필요했다.
4. frontend repository를 API 방식으로 교체한다 — 기존 store와 UI는 가능한 한 유지하려 했다.
5. localStorage migration과 실패 처리를 추가한다 — 이미 만든 task를 잃지 않아야 했다.
6. Weekly와 Monthly의 부족한 interaction을 보완한다 — 동기화된 데이터를 여러 화면에서 직접 다뤄보기 위해서였다.
7. landing과 Google 로그인을 정리한다 — 실제 사용자가 planner에 들어오는 경로를 마무리하려 했다.

## 만들면서 생긴 이슈

### Routine 연결만 지우면 같은 task가 다시 생겼다

특정 날짜의 routine occurrence만 독립 task로 바꾸기 위해 `Detach`를 추가했다. 처음에는 occurrence의 `repeatSourceId`만 지우면 된다고 생각했다.

하지만 anchor는 그 날짜에 occurrence가 없다고 판단하고 다음 materialization에서 같은 task를 다시 만들 수 있었다. detach할 때 anchor의 `excludedDates`에 원래 날짜도 함께 기록하도록 바꿨다.

```text
Routine occurrence
  -> repeatSourceId 제거
  -> anchor.excludedDates에 원래 날짜 추가
  -> 일반 task로 유지
```

이 규칙은 Weekly에서 occurrence를 다른 날짜로 옮기거나 삭제할 때도 사용했다. 반복 패턴 자체는 그대로 두고, 해당 날짜만 다시 생성하지 않는다.

### Scope와 deadline이 같은 날짜처럼 취급됐다

`scope`는 task를 언제 할지 정하지만, 마감일을 표현하지는 못했다. week scope task가 금요일까지 끝나야 할 수도 있다.

선택적인 `dueDate`를 추가하고 상세 화면에서 수정할 수 있게 했다. task row에는 `Due Today`, `Due Fri`, `Due Aug 14` 같은 badge를 표시한다. 지난 날짜이면서 미완료일 때만 빨간색으로 바뀐다.

고정된 due date는 반복 task와 맞지 않아 routine에는 editor를 숨겼다. 일반 task를 routine으로 바꾸면 기존 due date도 지운다.

### localStorage migration이 중간에 멈출 수 있었다

첫 API load에서 legacy localStorage task를 하나씩 server에 올리도록 했다.

```text
legacy key 확인
  -> local task를 각각 POST
  -> 전체 성공
  -> legacy key 삭제
  -> server list 다시 조회
```

일부만 올라간 상태에서 network error가 나면 localStorage를 지우지 않는다. 다음 load에서 전체 목록을 다시 보내고, 같은 id가 이미 존재하는 경우만 안전한 duplicate로 처리한다. 다른 validation error까지 duplicate로 넘기면 잘못된 task가 조용히 사라질 수 있어서 구분했다.

### 저장 실패 후 화면과 server 상태가 달라졌다

기존 localStorage repository에서는 write 실패를 거의 고려하지 않았다. API 연결 뒤에도 UI는 먼저 optimistic update를 하기 때문에 request가 실패하면 화면에만 변경이 남을 수 있었다.

write가 실패하면 error banner를 보여주고 server list를 다시 받아오도록 했다. 이후 오래 열어 둔 tab에서는 만료된 access token을 refresh한 뒤 요청을 한 번 재시도하게 했다.

### Monthly grid는 mobile에서 너무 좁았다

Monthly를 실제 7-column calendar로 바꾸자 desktop에서는 날짜와 task preview를 보기 쉬웠지만, mobile에서는 각 cell이 너무 좁았다.

mobile에서는 같은 grid를 축소하지 않고 주별 vertical agenda로 전환했다. 날짜를 선택하면 desktop은 오른쪽 `DayAgendaDrawer`, mobile은 full-screen sheet를 사용한다. agenda에서 task detail을 열었다가 닫으면 선택한 날짜로 돌아오도록 하나의 overlay stack으로 관리했다.

### Google 로그인을 기존 인증에 어떻게 넣을지 정해야 했다

새 인증 system을 추가하는 대신 Google Identity Services에서 받은 ID token을 Django가 검증하도록 했다. Django는 기존과 같은 Simple JWT pair를 발급하고, Next.js가 HTTP-only cookie에 저장한다.

```text
Google ID token
  -> Next.js /api/auth/google
  -> Django token verification
  -> Simple JWT pair
  -> HTTP-only cookies
```

돌아온 사용자는 Google의 stable `sub`로 찾는다. 같은 verified email의 password account가 이미 있으면 새 user를 만들지 않고 연결한다. Google-only account에는 사용할 수 없는 password를 설정했다.

## 완성된 흐름

7월 30일 오전 기준으로 다음 흐름이 동작했다.

```text
email/password 또는 Google로 로그인
  -> /planner 진입
  -> task 추가와 수정
  -> Django API에 사용자별 저장
  -> 다른 browser에서 같은 task 조회
  -> Daily / Weekly / Monthly에서 일정 관리
```

이번 구간에 완료한 내용은 다음과 같다.

- routine occurrence detach와 제외 날짜 처리
- scope와 분리된 due date
- 사용자별 Django task CRUD API
- Next.js task proxy와 API repository
- localStorage one-time migration
- sync error banner와 server resync
- Weekly drag-to-reschedule
- 실제 month grid와 day agenda
- `/app`에서 `/planner`로 route 이름 변경
- landing page의 실제 Daily preview
- Google Sign-In과 기존 account 연결
- access token refresh와 backend log 보완

## 개선점과 노트

- server를 source of truth로 사용하며 offline queue는 아직 없다.
- 여러 기기에서 동시에 수정할 때의 merge나 version 처리는 지원하지 않는다.
- Monthly에서는 drag-to-reschedule을 지원하지 않는다.
- 이 로그 다음 작업부터 일정에 속하지 않는 목표를 위한 Bucket List를 시작한다.
