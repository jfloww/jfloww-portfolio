## Goal

After importing my transactions, I wanted to answer a practical question: are simple keyword rules enough to organise my spending, or does an LLM do the job better?

To compare them fairly, I labelled real transactions by hand, separated the data used for improvement from the data used for evaluation, and measured accuracy, coverage, cost, and latency together. August 24 was the first time that complete workflow ran against a live model.

The day produced three prompt versions. Version 1 established the baseline, version 2 was rejected even though its macro F1 rose, and version 3 was designed on the development split and adopted after one benchmark measurement.

## Sketch

The evaluation path gives prompt work a development split separate from the frozen validation benchmark.

```text
742 imported transactions
  -> 400 rows labelled twice by one annotator
  -> merchant-disjoint split
       ├─ 265 development rows
       │    -> inspect failures
       │    -> choose prompt changes
       └─ 135-row frozen validation benchmark
            -> measure the chosen prompt once
            -> publish aggregate results only
```

Predictions are retained for failure analysis but never enter the repository or public artifact.

```text
live run
  -> archived aggregate report
  -> private row-level predictions
       -> failure analyser
       -> counts-only public JSON
```

## Plan

1. Build a reproducible 400-row subset without exposing counterparties.
2. Finish the taxonomy from annotation evidence rather than from the initial design.
3. Run rules, Claude Haiku 4.5, and the hybrid on the frozen benchmark.
4. Archive prompt, dataset, model, cost, latency, coverage, and accuracy together.
5. Record row-level predictions privately so a failure does not require another paid run to inspect.
6. Choose prompt changes on development and touch the benchmark only afterwards.
7. Publish aggregate results with containment tests covering both JSON and page copy.

## The First Live Result

Under `categorise/v1`, the frozen 135-row benchmark produced:

| System | Macro F1 | Weighted F1 | Accuracy | Coverage |
|---|---:|---:|---:|---:|
| Keyword rules | 0.0464 | 0.0549 | 0.0667 | 20% |
| Claude Haiku 4.5 | 0.4277 | 0.7201 | 0.6593 | 100% |
| Rules + Claude | 0.4223 | 0.7142 | 0.6519 | 100% |

The Claude run cost $0.2404 for 135 rows, or $0.00178 per row. Its p50 latency was 1,358 ms and p95 was 1,859 ms in the first archived run.

The difference between macro and weighted F1 matters. A typical row experiences a result near the weighted figure, while macro F1 gives every represented category equal weight and exposes how weak the model remains on small classes.

## A Prompt Change Rejected

Version 1 predicted `LIVING_OTHER` eighteen times even though the benchmark contained one true example. Version 2 added one rule making that label a last resort. The model, rows, split, taxonomy, scoring, and inference settings stayed fixed. The figures below are from the first paired v1–v2 runs.

| Metric | v1 | v2 |
|---|---:|---:|
| Macro F1 | 0.4277 | **0.4397** |
| Weighted F1 | **0.7201** | 0.7108 |
| Accuracy | **0.6593** | 0.6519 |
| Cost / row | **$0.001781** | $0.001864 |
| p95 latency | **1,859 ms** | 3,000 ms |
| `LIVING_OTHER` F1 | 0.1053 | 0.1053 |

Macro F1 rose while the target category did not move. Weighted F1, accuracy, cost, and p95 latency worsened; coverage remained 100%.

The reason was arithmetic. Macro F1 averages over the union of labels in the benchmark and labels the model predicts. Version 2 stopped predicting `LIVING_GYM`, a class it had never classified correctly, so the denominator fell from 21 labels to 20.

| | v1 → v2 |
|---|---:|
| Labels in the average | 21 → 20 |
| Summed per-label F1 | 8.9814 → **8.7936** |
| Macro F1 | 0.4277 → 0.4397 |

The mean rose while the sum fell. Version 2 was rejected and retained in the code so the archived result remains reproducible.

## A Prompt Change Adopted

The development split showed two failures that were not visible from the benchmark aggregate.

`REFUND` scored F1 0.0000 on nineteen development rows. The model often described a credit or refund correctly and then labelled the transaction by the original merchant category. It reasoned about what the merchant was before reasoning about the direction of money.

`TRANSFER` lost thirteen of twenty-six rows to `LIVING_CARD_FEE`. The model recognized a credit-card payment but confused paying a balance with being charged a membership fee.

Version 3 added two rules to v1, not to the rejected v2. The rules were checked against development gold before being written:

```text
card balance payment              -> TRANSFER
inbound person-to-person credit   -> REFUND
```

The selected benchmark result became:

| System | Macro F1 | Weighted F1 | Accuracy | Mean | p95 | Cost / row |
|---|---:|---:|---:|---:|---:|---:|
| Claude v1 | 0.4277 | 0.7201 | 0.6593 | 1,779 ms | 2,327 ms | $0.001781 |
| Claude v2, rejected | 0.4397 | 0.7108 | 0.6519 | — | — | $0.001864 |
| **Claude v3, selected** | **0.4724** | **0.7298** | **0.6667** | **1,472 ms** | **1,781 ms** | $0.001913 |

The public summary leaves v2 timing blank instead of combining its first archived run with the later v1 rerun in this table. Version 3 was selected because weighted F1 and accuracy improved as well as macro F1. Its recorded run was faster, but the runs were not repeated enough to attribute that latency difference to the prompt.

## The Development–Benchmark Gap

The most important result was not the new headline score.

| | Development, tuned on | Benchmark, independent |
|---|---:|---:|
| Macro F1 | 0.4263 → 0.5699 (**+0.1436**) | 0.4277 → 0.4724 (**+0.0447**) |
| Accuracy | 0.6302 → 0.7434 | 0.6593 → 0.6667 |
| `REFUND` F1 | 0.0000 → 0.6896 | 0.6667 → 0.6667 |
| `TRANSFER` F1 | 0.3111 → 0.7576 | 0.8421 → 0.8292 |

The fix transformed development and barely moved the benchmark. It also moved the benchmark through a different category. `REFUND` was already working there, so the failure the prompt was written to fix did not exist on that side. Most of the benchmark gain came from `LIVING_CARD_FEE`, which rose from 0.0000 to 0.5000.

The two merchant-disjoint splits presented different failure patterns in these runs. That observation is useful, but a single pair of runs is not proof of how much the prompt generalized or of what caused the gap.

Version 3 also reduced the macro denominator from 21 to 20, but unlike v2 its summed per-label F1 increased.

| | v1 → v2 | v1 → v3 |
|---|---:|---:|
| Summed per-label F1 | 8.9814 → **8.7936** | 8.9814 → **9.4480** |
| Macro F1 | 0.4277 → 0.4397 | 0.4277 → 0.4724 |

Version 2's gain was entirely arithmetic. Roughly half of version 3's macro gain came from better answers and half from the smaller divisor.

## Failure Analysis

Saving predictions made it possible to group errors without paying for inference again.

| Failure mode | Rows |
|---|---:|
| Abstention would have been better | 20 |
| Thin description, under 15 characters | 9 |
| Confident but wrong, at least 0.80 | 7 |
| Polysemous merchant | 5 |
| Annotators disagreed too | 3 |
| Rules right, model wrong | 1 |
| **Model right, rules wrong** | **82** |

Mean confidence was 0.8411 when correct and 0.6078 when wrong. Twenty wrong rows were answered below 0.60, mostly as `LIVING_OTHER`. This suggests the next useful change is a confidence-based abstention threshold rather than another prompt sentence.

## Rulings

### Disagreement between annotation passes is difficulty, not ambiguity

Thirty-one of the 400 rows received different labels from the two annotation passes. Converting those disagreements into acceptable-label sets would raise every score, but disagreement usually means one pass was wrong. Ambiguity remains authored only when a person records multiple defensible labels and explains why.

The disagreement rows are reported as a difficulty stratum instead. This measures whether the model struggles where a person did without claiming two answers were correct.

### Prompt changes are chosen on development

Version 2 was designed after inspecting the benchmark, which meant the same data was used to choose and evaluate the change. Version 3 was designed from 265 development rows and measured on the benchmark once afterwards. The CLI now makes this separation explicit.

### Predictions are recorded and never published

Row-level predictions make rescoring and failure analysis free, but they contain real transaction identifiers beside model output. They remain under a git-denied data path. Only aggregate counts and rates can reach the public artifact.

### A fitted rule baseline is a lookup table

Rules scored macro F1 1.0000 on the development split used to fit them. That is not evidence of perfect categorisation. On development, the rules-versus-model comparison measures memorization; only the merchant-disjoint benchmark can compare the systems fairly.

## What Went Wrong

### The line-ending check matched every line

`grep -c $'\r'` was intended to detect CRLF, but the pattern did not survive into grep and matched every line. Several “no churn” conclusions during the day were only line counts.

The real mechanism was found with byte-level checks: `Path.read_text` normalized line endings in memory and `Path.write_text` wrote `os.linesep` on Windows. A small edit could therefore turn into a whole-file rewrite.

The same bug happened again inside the commit documenting it. Writing this history entry with `Path.write_text` changed LF to CRLF and turned a 188-line addition into a 306/115 rewrite. The reliable rule is not to be more careful with `write_text`; it is to use `read_bytes` and `write_bytes` when line endings must be preserved.

### Public output checks did not cover the surrounding page

A real merchant name appeared in landing-page copy even though the aggregate JSON was clean. The payload containment test already scanned merchant names, but the prose around it did not. The test now checks every served page as well as the JSON.

### A typed cost summary disagreed with its computed field

One sentence described a 9.6% cost increase while the computed field beside it said 7.4%. The prose now binds to the computed value rather than duplicating the number by hand.

### UTC made the wrong local filename look plausible

Four run logs were initially named August 25 even though they were produced locally on August 24. The artifact's internal UTC timestamp was correctly on the 25th, which made the filenames look reasonable until local-date convention was checked.
