> **후속 기록 (2026년 8월 9일):** 아래에 남아 있던 health check, rollback, deployment 문제는 production을 Vercel, Cloud Run, Neon으로 옮기면서 정리했다. 현재 architecture와 수동 release flow는 [Log 6](/posts/picking-up-log6)에 기록했다.

## 목적

기능을 계속 추가하기 전에 backend를 한 번 멈춰서 다시 보기로 했다. 화면에서 정상적으로 동작하는 것과, 여러 request가 겹치거나 중간에 실패해도 데이터가 맞게 남는 것은 다른 문제였다.

이번에는 `docs/refining` 아래에 확인한 문제를 RF 번호로 기록하고 우선순위를 나눴다. 처음부터 완벽한 구조를 만들었다는 식으로 정리하기보다, 실제 code와 test를 보면서 어떤 가정이 틀렸는지 남기는 편이 더 중요했다.

```text
P0  security / data integrity
P1  backend reliability / operation
P2  measured need가 필요한 maintainability 작업
```

Log 5에서는 그중 task transaction, domain validation, authentication을 중심으로 정리했다.

## 스케치

backend의 책임을 네 단계로 나눠서 봤다.

```text
Frontend
  -> 빠른 interaction과 optimistic state

Serializer
  -> request shape와 cross-field rule

Service
  -> 하나의 user action에 필요한 transaction

Database
  -> API를 우회해도 깨지면 안 되는 invariant
```

모든 rule을 database에 넣는 것이 목표는 아니었다. JSON array 내부의 uniqueness나 scope별 date format은 serializer가 다루는 편이 명확하다. 반대로 단순한 column 관계나 uniqueness는 database가 마지막 경계가 되어야 했다.

## 계획

1. 현재 code와 문서를 대조해 실제 문제만 refinement register에 올린다.
2. 여러 API write로 구성된 task action을 atomic command로 바꾼다.
3. task version을 추가하고 stale write를 명시적으로 거부한다.
4. optimistic failure 뒤에 오래된 state가 다시 저장되는 경로를 찾는다.
5. field type 검사를 넘어 task 전체 의미를 validation한다.
6. password와 Google login의 실패 contract, timing, throttle을 점검한다.
7. local test와 Oracle에서 증명한 범위를 구분한다.

## Refining 과정에서 생긴 이슈

### 화면에서는 한 번의 action인데 server에는 두 번의 write였다

Nest는 target에 subtask를 추가한 다음 source task를 삭제했다. Promote는 새 task를 만든 다음 parent에서 subtask를 제거했다. routine occurrence를 detach하거나 삭제하거나 다른 날짜로 옮길 때도 occurrence와 anchor를 따로 저장했다.

두 번째 request가 실패하면 첫 번째 write만 남는다. 특히 occurrence만 사라지고 anchor의 `excludedDates`가 갱신되지 않으면 다음 materialization에서 같은 task가 다시 생길 수 있었다.

이 동작들을 Django service command로 옮겼다.

```text
request
  -> owner와 관련 task 조회
  -> expected version 확인
  -> row lock
  -> transaction.atomic()
  -> 전체 성공 또는 전체 rollback
```

`Nest`, `Promote`, `Detach`, `Delete occurrence`, `Reschedule`, `Reorder`가 같은 형태를 사용한다. task에는 증가하는 `version`을 두고, generic update와 delete는 `If-Match`를 요구한다. 오래된 version이면 덮어쓰지 않고 `409 Conflict`를 반환한다.

Reorder도 browser가 계산한 float를 저장하는 대신 `insertBeforeId`를 보낸다. server가 현재 sibling을 lock하고 neighbor가 아직 유효한지 확인한 뒤 order를 계산한다.

### Resync만 하면 optimistic state가 안전할 거라고 생각했다

command가 실패하면 server list를 다시 받아오는 처리는 이미 있었다. 처음에는 그것으로 충분하다고 봤다.

문제는 queue에 남아 있던 다음 edit였다. 실패 전에 만들어 둔 전체 task snapshot이 resync 뒤의 새 version과 함께 저장될 수 있었다. 예를 들어 Nest가 실패했는데 그 뒤에 target title edit가 queued되어 있으면, title과 함께 실패한 subtask 추가까지 server에 들어갈 수 있었다.

visible optimistic state와 authoritative snapshot을 분리했다. queued mutation은 전체 task가 아니라 field delta, subtask upsert/remove 같은 intent를 저장한다. 실패하면 resync가 끝날 때까지 기다린 뒤 그 intent를 새 server state 위에 다시 적용한다.

```text
failed mutation
  -> server state reload
  -> remaining intent rebase
  -> 사라진 entity는 no-op
  -> 다음 mutation 실행
```

routine의 제외 날짜는 array 전체를 덮어쓰면 다른 session이 추가한 날짜를 잃는다. 그래서 새로 추가한 날짜만 patch에 기록하고, rebase할 때 set union으로 합치도록 따로 처리했다.

review 중에는 queue failure handler 자체가 throw하면 이후 mutation이 전부 멈추는 경우도 찾았다. promise chain 끝에 방어용 `.catch()`를 추가했고, browser task request에는 15초 timeout을 두었다. global queue 구조는 유지했지만 하나의 멈춘 request가 무기한 전체를 막지는 않게 했다.

### Field가 각각 유효해도 task 전체는 말이 안 될 수 있었다

기존 serializer는 type과 length는 확인했지만 field 조합의 의미까지 검사하지 않았다. 그래서 API만 직접 호출하면 다음과 같은 state를 만들 수 있었다.

- repeat anchor이면서 동시에 generated occurrence인 task
- repeat schedule 없이 `excludedDates`만 가진 task
- routine-managed task에 고정 `dueDate`가 있는 경우
- `time` 없이 `durationMinutes`만 있는 경우
- 같은 id의 subtask가 한 task 안에 두 번 들어가는 경우

`TaskSerializer.validate()`에서 partial PATCH까지 현재 instance와 합쳐 검사하도록 바꿨다. repeat weekday 중복과 date/time format을 확인하고, `subtasks`와 `excludedDates`에는 방어적인 최대 개수도 뒀다.

database constraint는 portable하게 표현할 수 있고 우회 경로에서도 반드시 지켜야 하는 관계에만 사용했다. JSONField 내용, regex, list uniqueness까지 억지로 constraint에 넣지는 않았다.

판단 근거가 약한 rule도 하나 있었다. 현재 UI에서는 time을 주로 day task에서만 편집하지만, 그것만으로 다른 scope의 time을 backend에서 거부할 근거는 부족했다. 이 rule은 추측으로 추가하지 않고 열어 두었다.

### Login 실패 경로마다 처리 비용과 response가 달랐다

password login은 직접 User를 조회한 뒤 JWT를 만들고 있었다. 존재하지 않는 email은 password hashing을 건너뛰기 때문에 account 존재 여부가 timing 차이로 드러날 수 있었고, wrong password와 inactive user의 response도 표준 Simple JWT contract와 달랐다.

`TokenObtainPairSerializer`를 확장하는 방식으로 바꾸고, email lookup은 Django authentication backend가 담당하게 했다. user가 없거나 case-insensitive duplicate가 있어도 dummy password hash 비용을 지불한 뒤 같은 401로 실패한다. Django admin의 username login은 기존 `ModelBackend`를 뒤에 유지했다.

login, registration, Google sign-in에는 endpoint별 burst와 sustained throttle을 추가했다. 여기서도 첫 구현이 끝은 아니었다.

DRF는 모든 throttle을 순서대로 평가하기 때문에 burst limit에서 이미 거절된 request도 sustained daily budget을 소비했다. 빠른 몇 번의 실패가 하루 quota까지 줄이는 구조였다. 첫 throttle이 거절하면 뒤의 throttle을 평가하지 않는 mixin으로 바꿨다.

또 production에서 `DJANGO_NUM_PROXIES=0`을 그대로 두면 nginx 뒤의 모든 request가 `127.0.0.1` 한 IP로 보인다. 그러면 한 사용자의 실패가 site 전체 login budget을 소모할 수 있었다. production 설정에서 proxy 수가 빠지면 Django가 시작 단계에서 실패하도록 guard를 추가했다.

### Concurrent auth race는 pre-check만으로 막히지 않았다

registration에서 `email__iexact`로 먼저 조회해도 두 request가 동시에 통과할 수 있다. 최종 경계는 database unique constraint이고, loser의 `IntegrityError`를 같은 validation error로 바꿔야 했다.

처음 fix에서는 `IntegrityError`가 난 transaction 안에서 어떤 field가 충돌했는지 다시 query했다. 이 상태의 transaction은 이미 깨져 있어 `TransactionManagementError`가 발생했다. insert를 별도 `transaction.atomic()` savepoint로 감싼 뒤 바깥에서 email과 username collision을 다시 확인하도록 수정했다.

Google account linking에도 비슷한 race가 있었다. 같은 password account에 두 요청이 동시에 identity를 만들려고 하면 loser가 500을 반환했다. savepoint 안에서 create를 시도하고, unique conflict가 나면 database winner를 다시 읽도록 바꿨다.

Django가 429와 `Retry-After`를 제대로 반환해도 Next.js BFF가 모든 auth error를 400으로 바꾸고 header를 버리는 문제도 있었다. BFF가 upstream status와 throttle header를 그대로 전달하도록 공통 error 처리를 정리했다.

### Test 환경도 production contract를 따라야 했다

GitHub Actions에 backend와 frontend job을 추가했다. 첫 remote run에서 backend는 통과했지만 frontend route integration test 아홉 개가 한꺼번에 실패했다.

production code는 `DJANGO_API_BASE_URL`을 읽고 있었지만 test router만 `localhost`를 hardcode하고 있었다. CI에서는 같은 server를 `127.0.0.1`로 지정해 모든 request가 예상하지 않은 origin으로 처리됐다. production과 test가 같은 environment contract를 사용하도록 고쳤다.

CI는 현재 Django check, migration drift, backend tests와 frontend tests, lint, build를 각각 실행한다. test 개수는 계속 바뀌기 때문에 글에는 고정 숫자를 넣지 않았다.

## 완성된 흐름

이번 refining에서 정리한 내용은 다음과 같다.

- versioned task resource와 `If-Match` precondition
- atomic Nest, Promote, Detach, Delete-occurrence, Reschedule, Reorder command
- server-owned reorder와 task creation order
- authoritative snapshot과 intent rebase를 사용하는 optimistic queue
- cross-field task validation과 필요한 database constraint
- Simple JWT contract에 맞춘 email authentication
- endpoint별 auth throttle과 proxy configuration guard
- registration과 Google identity linking의 concurrent race 처리
- auth BFF의 upstream status와 `Retry-After` 전달
- backend/frontend를 분리한 GitHub Actions CI
- 해결 여부와 검증 범위를 기록하는 refinement register

## 개선점과 노트

- routine materialization과 rollover는 아직 browser가 시작한다. 같은 anchor와 날짜에 두 session이 서로 다른 occurrence를 만들 수 있어 server-owned idempotent command가 필요하다.
- 동시에 여러 request가 access token refresh를 시작하는 경우를 한 번으로 합치는 처리는 아직 없다.
- API error body는 endpoint마다 형태가 다르다. status 전달은 고쳤지만 공통 error envelope은 남아 있다.
- health check, rollback 절차, request correlation을 포함한 production operation은 더 보완해야 한다.
- SQLite에서는 `select_for_update()`가 실제 row lock처럼 동작하지 않는다. Oracle test schema 권한 문제를 해결하고 contention을 직접 확인해야 한다.
- Python dependency pinning과 build reproducibility도 아직 정리할 부분이 있다.

이번 작업에서 가장 많이 바뀐 것은 code 양보다 확인 방식이었다. “UI가 이 값을 보내지 않는다”거나 “두 request가 보통 연달아 성공한다”는 설명은 보장이 아니었다. 그런 문장을 찾을 때마다 serializer, transaction, database constraint, test 중 어디에서 실제로 막을지 정했다.
